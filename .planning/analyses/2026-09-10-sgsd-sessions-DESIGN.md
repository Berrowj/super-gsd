# SGSD owned worktree sessions

Status: APPROVED by operator instruction to start working through the general session workflow, 2026-09-10. Implementation authority: 170-14-OWNED-SESSIONS-PLAN.md in the isolated Windows development branch. Not deployed. Does not expand or compete with remote 170-13.

## User outcome

After connecting to DEVCP, Jack asks SGSD to create tmux sessions for named worktrees. The system resolves the requested worktrees, establishes one fleet coordinator, and gives each worktree one Fable orchestrator with its normal Codex worker bridge. The operator can tell which actual session produced observed telemetry and which evidence is missing.

## Approaches considered

1. Skill alone: smallest text change, but no enforcement when another agent directly invokes tmux or starts bare Claude.
2. Skill plus existing-launcher integration and launch receipts: recommended. Reuse working preparation, registration, worker transport and monitoring; add only the absent ownership binding and truthful launch/status checks.
3. New supervising daemon/collection stack: out of scope. Introduces another lifecycle and unnecessary complexity.

## Recommended design

- New globally installed `super-gsd/skills/sgsd-sessions/SKILL.md`, naturally triggered by requests to open/create/recover DEVCP tmux worktree sessions. Explicit command name is proposed, not available yet. Existing installer discovers SGSD skill directories; do not add a parallel GSD/pi skill installation path.
- Reuse `sgsd-remote-tmux.sh` and `global.cjs prepare`. Preserve Claude-in-terminal topology. No new collector, Prometheus stack, native accounting scheme or copied gate implementation.
- Small private, versioned fleet registry/launch receipt: coordinator ID, real worktree/project ID, actual Atlas run UUID, tmux server/session/pane identity, actual provider PID/start identity, source/install/pin evidence, role and handover reference. Coordinator is a recoverable ownership record, not an always-running extra LLM. Do not confuse launcher preliminary run labels with the UUID generated by prepare.
- Serialize ownership claims and session creation; reject competing owners or an already owned real worktree unless an explicit handover is acknowledged. Existing-session name reuse requires verifying project/run/process bindings, not tmux name alone. Absent/stale owner evidence does not authorize killing or silently adopting a process.
- Prelaunch: resolve requested existing worktrees, inspect protected changes, check source/pin/runtime provenance and hook paths, check shared receiver without live provider probes. Missing worktree requires ordinary authorized worktree creation, not guessed branch creation. Do not change pins to bypass provenance.
- Launch through the existing supported path. Start paused/read-only until identity and handover acknowledgement are verified. Capture a machine-readable receipt after the actual provider process exists. `launcher_session_start` emitted during prepare is not readiness proof.
- Read-only session-start briefing reuses 170-13 when available: receiver healthy; this exact session/root registered; native delivery observed/timestamp or pending/stale; operational delivery observed/degraded with gaps/backlog. A wrong-project registration is never this project's attachment.
- Report worker communication separately using existing exact worker/thread/turn/request and owner-scoped control receipts. Queued/applied is transport status, not consumption or success. Routine startup checks do not generate live worker probes or expensive model canaries.
- Show ATC/MUDA/gates as configured, observed, degraded, or not exercised. Match existing genuine evidence to source/receipt/canonical records; never manufacture successful gate rows to make boot green. Project-only operational evidence is not claimed as exact session attribution.
- Bare/manual launches cannot acquire startup environment retroactively from a read-only hook. Warn and offer a supported handover/relaunch. No automatic process stops or extra stack activation from SessionStart.
- Join fleet metadata to existing telemetry IDs; do not duplicate token totals or export prompts/credentials/handover bodies. Historical gaps remain visible. Monitoring and verified evidence-copy status stay distinct from ingestion health.

## Failure behavior

Incorrect provenance/ownership/identity prevents unattended work. A newly registered session with no delivery yet reports pending; bounded waiting cannot turn missing evidence into success. A healthy idle session may show stale-or-idle instead of a fabricated freshness heartbeat. Routine diagnostic checks are deterministic and bounded with zero extra model turns.

## Required tests before deployment

Baseline agent scenario without the new skill, then forward test with it; record observed behavior, not only wording matches. Isolated tests cover concurrent owner claims, wrong-project session-name collision, stale PID reuse, partial launch, unregistered manual boot, fresh registration without delivery, receiver health versus delivery, gate not exercised, and no-model routine probes. Test installer propagation and a single scoped fresh supported DEVCP launch. Use existing registered review/gates under the numbered plan; preserve live sessions and original evidence throughout.

## Scope boundary

Linux/DEVCP first. No Windows capture claim; no global shutdown, force reset, automatic provider/model substitution, historical billing completeness claim, or telemetry/dashboard redesign. User-facing natural-language session creation and ownership receipt are the feature, not a new orchestration engine.
