SGSD Pro Mode: control plane + Codex execution fabric

The upgrade is not “let Codex run everything”. The win is a typed, auditable execution system where SGSD owns state, gates, memory and promotion — while Codex handles planning, bounded execution, goal loops, review and specialist safety checks.

Current foundation

What SGSD already has

The repo already points in the right direction: Opus/Claude orchestrates, Codex performs research/planning/code/gates, source mutation is locked behind Codex, and bounded tasks can route through temporary worktrees.

Runtime role split

Opus/Claude reads `.planning/`, decides next step and synthesises results. Codex GPT‑5.5/xhigh handles research, planning, code work, verification, ATC, gates and MUDA.

Codex executor lock

Source-changing executor work is already routed through `super-gsd/scripts/codex-executor.sh`, with read-pack patch fallback for Windows host read blocks.

Double-agent router

Bounded task capsules can route to local scripts, Codex or Claude. Codex execution uses a temporary git worktree, allowed-files checks, acceptance commands and patch/report output.

Isolated exploration lane for alternative implementations, app threads and PR drafts.

codex.plan

Use when the task is complex, ambiguous or architectural. It should not mutate source. It produces a plan artefact SGSD can challenge, revise and lock.

  • Inputs: state, roadmap, phase notes, constraints.
  • Outputs: PLAN-DRAFT.md, risks, file scope, acceptance commands.
  • Gate: no source changes until PLAN-LOCKED.md exists.

North-star architecture

SGSD = control plane. Codex = specialist execution fabric. Hooks = guardrails. Skills = reusable behaviours. `/plan` = plan drafting. `/goal` = long-running phase finisher. `/review` = independent code reviewer. ATC = final authority.

The one thing not to do

Do not turn Pro Mode into “Codex, run the repo”. Turn it into “SGSD, choose the best Codex lane, enforce the contract, observe the work, review the result, then promote only when gates pass.”
