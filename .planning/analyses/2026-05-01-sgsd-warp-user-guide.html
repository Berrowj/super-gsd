The mental model

Think of SGSD as the operating system for building a serious software project. Warp is not the source of truth. Warp is the cockpit, command launcher, multi-pane workspace, and optional AI assistant around SGSD.

Architecture
Product repo

The application you are building: source files, tests, package files, docs, deploy config.

.planning

SGSD truth: STATE.md, milestones, phases, plans, verification, ATC reviews, metrics ledgers.

super-gsd

The harness tools: gates, cockpit, MCP server, token tools, Codex routing, validators.

.warp

Operator shortcuts: workflows that run known-good SGSD commands from Warp Command Palette.

Warp Agent

Optional AI assistant. Useful when it calls SGSD MCP tools. Costs Warp credits when used.

Why this matters

The hard part is not typing commands

The hard part is keeping long autonomous software work honest: what phase is active, what passed, what failed, what Codex did, where tokens went, what evidence exists, and how to resume.

Warp gives those questions a command surface. SGSD gives them a truth surface. Together they reduce guessing, stale scrollback, hidden failures, and operator memory load.

Key rule: Workflows and launch configs are just local terminal commands. They do not spend Warp credits.

Where to run each thing

This is the practical part. Some commands should run in the current Warp tab. Some are better in a fresh tab. Launch configurations open a new window on Windows. The reason is session clarity.

Starting SGSD
Where: current Warp tab in the project root.
sg
Why: Claude should stay in the tab where you typed the start command. SGSD opens cockpit separately so the main AI session remains visible and easy to resume.
Starting autonomous mode
Where: same main Claude tab, or workflow if you intentionally want a run to start.
sg -Go
Why: this begins real autonomous work. Do not run it casually in a throwaway tab unless you mean to start SGSD.
Status, doctor, gates, tokens
Where: fresh Warp tab, side tab, or current tab. Use Command Palette: Ctrl+Shift+P, then SGSD:.
Why: these are read-only checks. A fresh tab keeps your Claude prompt clean while you inspect state.
Launch configurations
Where: Warp Command Palette, search Launch Configuration: SGSD.
Why: on Windows these open a new Warp window. Treat them as saved workspaces, not as panes injected into your current window.
Warp Agent + MCP
Where: Warp Agent panel. Ask it to call a specific SGSD MCP tool, such as sgsd_current_state.
Why: useful for explanation. This is the part that spends Warp credits, because Warp Agent is doing AI reasoning.

Daily operating routine

Most days you only need a small loop: start, inspect, let SGSD run, review evidence, recover if needed. The deeper tools are there for diagnosis and project handoff.

Morning start

Bring the harness online

cd C:\Users\\GSDedits sg

Use this in the main project tab. The cockpit opens separately. Claude stays in the tab where you typed sg.

Quick health check

Ask what is happening

Ctrl+Shift+P SGSD: Status SGSD: Watchdog Status SGSD: Codex Status

These are local commands. They cost no Warp credits and are safe to run while SGSD is working.

If something feels wrong

Diagnose before touching state

SGSD: Warp Doctor SGSD: Recovery Packet SGSD: Gate Status

Do not hand-edit STATE.md first. SGSD is designed to reveal what drifted and what repair command is safe.

Using this in a fresh project repo

In the next project, the point is not to copy this exact repo's state. The point is to install or scaffold SGSD into the new repo so every milestone gets the same audited build loop.

Fresh repo sequence
  1. Open the new repo root in Warp.
  2. Ensure SGSD scaffold exists: .planning/, super-gsd/, .warp/workflows/, AGENTS.md, WARP.md.
  3. Run sgsd-setup if private memory or knowledge roots need configuration.
  4. Run SGSD: Warp Doctor to verify the local setup.
  5. Run SGSD: MCP Self-Test if Warp Agent will be used for structured status.
  6. Define the first milestone and phase plan through SGSD, not by ad hoc edits.
  7. Start with sg or SGSD: Start.
What carries across

The workflow names, launch configs, MCP tool names, and operating rules should feel the same in every repo. The data changes: milestones, phases, gates, commits, artifacts, and token spend all become specific to that project.

Why this helps: you do not relearn the operating model for every software project. Each repo has a consistent control plane, but the evidence stays local to that repo.

MCP and Warp credits

MCP is the structured data pipe. It lets an assistant ask SGSD for current state, gates, tokens, Codex status, recovery packet, and artifacts instead of guessing from scrollback.

Free local use

These do not spend Warp credits:

SGSD: MCP Self-Test
cd C:\Users\\GSDedits node super-gsd/tools/warp-mcp/run-self-test.cjs
{"jsonrpc":"2.0","method":"tools/list","id":1} | node super-gsd/tools/warp-mcp/server.cjs

The server is local Node.js over stdio. It only costs machine time unless you ask Warp Agent to reason over the response.

Credit-spending use

These use Warp credits because Warp Agent is thinking:

Use the SGSD MCP tool sgsd_current_state and tell me the current milestone, phase, stale sources, and recommended repair. Do not inspect scrollback.

The MCP call itself is local. The credit spend is the AI interpretation, summarization, and reasoning inside Warp Agent.

Claude, Codex, Warp Agent

These are not interchangeable. They are different seats in the SGSD operating model.

Actor Best use Do not use it for
Claude Code Run SGSD, coordinate phases, make judgment calls, repair state through the orchestrator. Quick one-off status questions when MCP can answer more cleanly.
Codex Bounded code edits, reviews, test fixes, implementation tasks with clear files and tests. Owning SGSD state or bypassing SGSD gates.
Warp Agent + MCP Operator explanations: what phase, what failed, why stale, where tokens went. Autonomously changing SGSD state or overriding gate results.
Workflows Running known local commands without remembering syntax. Reasoning or summarizing. They are buttons, not brains.
Rule of thumb: Claude runs SGSD. Codex edits code. Warp Agent explains SGSD through MCP. Workflows run local commands.

Troubleshooting guide

When something looks wrong, start with the diagnostic surfaces. The goal is to identify whether the problem is Warp setup, SGSD state, Codex routing, gates, or stale context.

Warp Doctor shows state_md_freshness missing

This means SGSD state files are stale relative to newer activity. It is not a Warp install problem.

SGSD: Recovery Packet SGSD: Start /sgsd-orchestrate go

Ask Claude to re-sync canonical SGSD state from the latest milestone artifacts. Do not hand-edit first.

Codebase Context is manual-check-required

Warp does not expose Codebase Context state to the terminal. Check it in Warp UI: Settings, AI, Codebase Context. Confirm the repo is indexed and .warpindexingignore is respected.

Workflows do not appear

Press Ctrl+Shift+P, not plain Ctrl+P. Search SGSD:. If still missing, run:

node super-gsd/tools/warp-workflow-lint/lint.cjs --project C:\Users\\GSDedits
MCP tools are not available in Warp Agent

First test locally:

node super-gsd/tools/warp-mcp/run-self-test.cjs

Then check ~/.warp/mcp_servers.json. Warp may need a restart after config changes.

Launch configurations do not show

On Windows, Warp reads launch configs from its Windows data path. Also check ~/.warp/launch_configurations because this repo keeps operator copies there. Re-run Warp Doctor and verify it counts YAML files.

Codex looks stale

Use:

SGSD: Codex Status SGSD: Route Decisions Recent

The first tells you whether Codex is active or stale. The second tells you why SGSD chose Claude or Codex.

Operator rules

These keep SGSD useful rather than turning it into a pile of shortcuts.

Do
  • Use SGSD: Warp Doctor before guessing.
  • Use workflows for local checks instead of asking Warp Agent every time.
  • Use MCP when you need structured truth.
  • Use launch configs when you want a repeatable workspace.
  • Let Claude/SGSD repair SGSD state through the orchestrator.
  • Use Codex for bounded code execution and review.
Do not
  • Do not bypass gates because a workflow feels inconvenient.
  • Do not hand-edit STATE.md as your first repair move.
  • Do not trust scrollback over .planning/ evidence.
  • Do not ask Warp Agent to mutate SGSD state casually.
  • Do not treat launch configs as active-window pane injection on Windows.
  • Do not spend Warp credits for simple local status checks.
The benefit: every new project gets the same operating discipline: start, inspect, execute, audit, recover, review, and ship by evidence instead of memory.
