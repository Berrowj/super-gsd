# Phase 97.5 - Context

Make it mechanically impossible to close a phase whose acceptance criteria are 100% structural.

## Why this phase exists (the incident)

On 2026-05-18 the Clarity ERP project surfaced six consecutive phases (v22-09 through v22-13) that all closed PASS while the audit-gate they were building did not actually work end-to-end. SO 130018965 — a real, closed-and-invoiced sales order with a present Quotation, DeliveryNote and Invoice in its chain — returned `overall_verdict: FAILED` from the engine.

The audit framework caught nothing because every PASS gate measured shape, not meaning:

- "Does the envelope JSON have `schema_version="1.0.0"`?" ✓
- "Does the writeback set `v22_12_review_state`?" ✓
- "Is the field written for 14/14 SOs?" ✓
- "Are out-of-scope leaks zero?" ✓

None of the gates asked: "for SO 130018965, does the engine return PASS?" That single assertion would have failed on every commit since the engine landed. Nobody wrote it.

The 14/14 at 100% blocked across a random Mongo sample was statistically impossible — every order broken contradicts an ERP that visibly works for accounting. The phase close treated it as a data observation, not a smell.

Full transcript and root-cause analysis: see DLB-07.

## Goal

Add a single required field to the SGSD v2 plan schema — `semantic_acceptance_criteria` — and make `validate.cjs` reject any plan that omits it. Each entry must declare an input, an expected outcome, and a verification command that runs against real data (not fixtures).

This is the plumbing layer of a multi-layer protection. Layers 3 (audit-gate close enforcement) and 4 (re-audit of existing v2.9 phases against the new rule) are scoped as follow-ups, not part of P97.5.

## Required Outputs

1. `super-gsd/templates/plan-schema-v2.json` — add `semantic_acceptance_criteria` as a plan-level **required** array of objects. Each object has required keys `input`, `expected_outcome`, `verification_cmd`. minItems: 1.
2. `super-gsd/tools/plan-schema/validate.cjs` — emit new error code `SCHEMA-09` when the array is absent or empty; `SCHEMA-10` when an entry is missing one of the three required keys.
3. Tests under `super-gsd/tools/plan-schema/` — cover: present-and-valid, absent, empty array, missing key per object, three-entry array. AAA pattern. No fixtures other than inline JSON.
4. Validate every existing v2.9 plan against the new schema and capture which plans need backfill. Output: `97.5-BACKFILL.md` listing each plan + missing field. **Read-only audit** — do not modify the existing plans in this phase.

## Out of Scope (deferred)

- Audit-gate enforcement of semantic ACs at phase close. `sgsd-audit` has no canonical source in this repo (only an installed copy at `~/.claude/commands/sgsd-audit/SKILL.md`). Adding canonical source is a separate phase.
- Backfilling existing v2.9 plans with semantic ACs. P97.5 only identifies the gap; backfill is per-phase work.
- Layer 5 in DLB-07 (re-audit v22-era debt) — Clarity-side, not this repo.

## Non-Negotiable Rules

1. The semantic AC's verification command must run against real data — production Mongo doc, real API response, real file on disk. Fixtures don't count.
2. Each semantic AC must be falsifiable: "for known-good input X, the system produces verdict Y" — not "the test passes".
3. The validator change is backward-breaking by design. Existing plans without the field WILL fail validation. That's the point. The orchestrator must surface this clearly at plan-check, not silently warn.
4. Codex owns the schema + validator + tests. Claude orchestrates only.

## Success Criteria

- `validate.cjs --plan-file <plan>` exits 1 with SCHEMA-09 when `semantic_acceptance_criteria` is missing.
- `validate.cjs --plan-file <plan>` exits 0 when the array has ≥1 fully-populated entry.
- Test suite passes (≥5 cases per the list above).
- BACKFILL.md lists every v2.9 plan that needs a semantic AC retrofit.
- DLB-07 committed in `.planning/decisions/`.
- SGSD memory entry committed in `.planning/memory/architecture/patterns/`.
