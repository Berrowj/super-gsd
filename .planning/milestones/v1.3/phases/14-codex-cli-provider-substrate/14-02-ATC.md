## 7-Step Findings

### 1. First Principles
Every new file is load-bearing. `review-providers.yaml` is required by
D-05/D-05a; `providers-registry.cjs` is required to read it; gates.yaml
edit is required by D-09a; `sgsd-codex-reviewer.md` by D-12. The
question mark was `sgsd-code-reviewer.md` (P3) — is it real or a
rename-rule violation? **Real.** It declares a v2 handover contract
(`invocation: agent`, `report_contract: code-reviewer-v1`, frontmatter
+ 4 XML blocks with a `code-reviewer-v1` 5-field output declaration
verbatim-identical to the Codex sibling). That's enrichment beyond
passthrough; it earns the `sgsd-` prefix per `feedback_sgsd_rename_rule.md`.
The `agent_subagent_type: gsd-code-reviewer` frontmatter legitimately
delegates implementation to the legacy agent while the stub owns the
contract — which is exactly the enrichment pattern the feedback rule
describes.

### 2. Delete
Nothing mass-deletable without losing a documented contract.
`review-providers.yaml` enum block (`invocation_types: [agent, shell]`
+ reserved comments) is 11 lines but it's the schema declaration — it
IS the documentation. `providers-registry.cjs` header JSDoc (L3-25)
is thorough; could be trimmed 5-8 lines, but it mirrors `gates-registry.cjs`
and consistency beats brevity here. `DEFAULT_CONFIG` object (L47-54)
could be read from a single source of truth (the ping in 14-03's
config.json patch), but doing so would require loading config.json at
module-init time — and the whole point of the "warn, don't throw"
fallback is that the module must boot even if config.json is absent.
So the duplication is intentional and load-bearing.

### 3. Simplify
`resolveReviewerProvider` bridge logic (L149-156, 8 lines) is close to
minimal. Structure: `getGate → if no reviewer_agent return null → pick
name (gate.reviewer_provider OR config.default_provider) → getProvider`.
Four sequential steps, zero nested conditionals, zero redundant `null`
checks. Good. One subtle issue: the null-check uses
`gate.reviewer_agent === undefined`, not `!gate.reviewer_agent`, so a
future gate with `reviewer_agent: null` would pass the null-check and
fall through to default-provider lookup. Consistent with JS strict-equality
conventions; not a bug, just noted.

### 4. Accelerate
N/A — registry is cold-start load-once, not a hot path.

### 5. Automate
Should there be a schema validator running at load? **No, not yet.**
The 2-provider static registry doesn't justify adding ajv or a
hand-rolled validator right now; Phase 15 dispatch path is the natural
home per Non-goal in plan. `getProvider` hard-error on unknown names
(L97) is the minimum useful automated check and it's present — that
covers D-06a typo-catch. Could add state enum validation (reject
`state: foo`) but D-15b says all rows state:active at ship, so
meaningful only post-v1.3.

### 6. Validate
Of the plan's 7 verification commands, 5 pass cleanly. The getProvider
assertion in plan §T2 is **broken** (`g.invocation_type !== 'agent'` —
the YAML field is `invocation`, not `invocation_type`; the record emits
`invocation: 'agent'`, so `g.invocation_type` is undefined and the
assertion always fires `process.exit(1)`). See W-3. The
resolveReviewerProvider assertion passes for `per-dispatch-ATC` but
reveals the semantic gap in W-1 when extended to `classifier-haiku`
(returns `claude-sonnet-reviewer`, not `null`). All file-existence and
frontmatter-field checks pass. gates.yaml has `reviewer_provider:

still `2.0.0`, not `2.1.0`, and `last_updated:` is `2026-04-22`, not
`2026-04-23` — see W-2.

## Warnings

- **W-1 (semantic gap): `resolveReviewerProvider` returns default provider
  for haiku-agent gates.** The null-check at `providers-registry.cjs:151`
  reads `gate.reviewer_agent === undefined`. This correctly returns
  `null` for gates with no `reviewer_agent` field
  (`sgsd-recall-queries`, `intent-injection`, `MUDA-waste-audit`,
  `sgsd-curate-learnings`, `token-log`, `verifier-row-arithmetic`,
  `verifier-detail-vs-summary`). But `classifier-haiku` and
  `context-selector-haiku` have `reviewer_agent: haiku` — the field IS
  defined, so the null-check passes, and the function returns
  `claude-sonnet-reviewer` via the config.default_provider fallback.
  **`haiku` is not a code-reviewer provider**; it's a classifier agent
  primitive. A Phase 15 consumer iterating gates and calling
  `resolveReviewerProvider` on each would incorrectly treat these two
  gates as reviewer-shaped. The plan's A4 test case doesn't exercise
  this scenario (tests `per-dispatch-ATC` and implies any non-reviewer
  gate, but the code was written against the "no field at all"
  interpretation). Code matches the plan's literal JSDoc spec; the
  spec itself is incomplete. **Fix options:** (a) narrow the predicate
  to `gate.reviewer_agent === undefined || gate.reviewer_agent === 'haiku'`;
  (b) check `gate.category === 'code-quality'` instead; (c) require
  the gate to declare `reviewer_provider:` explicitly to count as
  reviewer-shaped (i.e. remove the default-provider fallback from this
  call site — callers who want default behavior can read
  `loadReviewProvidersConfig().default_provider` themselves). Option
  (c) is the cleanest and closes the semantic gap while preserving
  separation of concerns. Phase 15 wire-up will likely rediscover
  this; capturing it now as a Phase 15 entry condition.

- **W-2 (plan-to-code drift): `gates.yaml` header not bumped.**
  Plan §T3 sub-bullets 3–4 say "bump `registry_version: 2.0.0 →
  2.1.0`" and "update `last_updated:` to `2026-04-23`". Committed
  diff (`a29136d`) is +2 lines only — the two `reviewer_provider:`
  row additions. Header still says `registry_version: 2.0.0` and
  `last_updated: 2026-04-22`. Review-brief notes "executor report
  noted plan §T3 said to bump but prompt said don't" — so this is a
  plan-vs-orchestrator-prompt drift that the executor resolved
  correctly for atomic-commit discipline (one commit = one thing =
  row edits; version bump = separate commit). Not a code bug.
  Action: either (a) ship a follow-up commit bumping
  `registry_version` to 2.1.0 + `last_updated` to 2026-04-23 (honors
  the plan and the `feedback_commit_discipline` pattern — schema
  changes should advertise version bumps so consumers see a new
  version); or (b) amend plan 14-02 §T3 to drop the bump directive
  and note that gates.yaml version bumps happen on schema changes,
  not row additions (field is schema-optional, so 2.0.0 → 2.0.1
  patch at most, not 2.1.0 minor). Recommend (a) — the new
  `reviewer_provider:` field IS a schema extension, even if backward-
  compatible, and 14-04's contract-check harness may key off the
  version.

- **W-3 (plan verification authoring bug): `g.invocation_type !==
  'agent'` assertion is broken.** Plan §T2 first verification command
  asserts `g.invocation_type !== 'agent'`. The YAML field is
  `invocation:` (no `_type`), so `g.invocation_type` is always
  `undefined`, and the assertion fires `process.exit(1)` every time.
  Either the executor skipped this command, or ran it and treated
  the exit-1 as a non-blocker. Neither is ideal. The loaded record
  has `invocation: 'agent'` (confirmed via manual repro). Fix: amend
  plan §T2 verification to `g.invocation !== 'agent'`. Non-blocking
  for this ship — `getProvider` works correctly, the assertion is
  just misnamed.

## Info

- **I-1 (naming)**: YAML enum block header is `invocation_types:`
  (plural) at line 32, but the field name on records is `invocation:`
  (singular, no `_type`). Internally consistent — the enum block
  names the set of values the `invocation` field can take — but a
  skim-reader may expect the field name to match the enum name.
  Consider renaming the block to `invocation_values:` or adding a
  one-line comment "(values for the `invocation:` field below)" for
  disambiguation. Cosmetic; doesn't affect parsing.

- **I-2 (cache-key drift)**: `loadProviders(yamlPath)` caches on first
  call with any yamlPath and ignores the path on subsequent calls.
  Same pattern as `gates-registry.cjs:38-55` (parity preserved), so
  no regression. But a test or tool passing a different `yamlPath`
  after cache warm-up silently gets the old cache. The JSDoc warning
  at L32-36 addresses this indirectly ("long-running processes that
  hot-swap ... MUST call resetCache()"). Consider either (a) making
  path part of the cache key; (b) explicitly warning if the passed
  path differs from the cached path. Low priority — no current
  caller swaps paths.

- **I-3 (API ergonomics)**: `resolveReviewerProvider(gateName,
  gatesRegistry, opts)` takes a dependency-injected gates-registry
  module, which means callers must do something like
  `{ getGate: (name) => g.getGate(name, gatesPath) }` if they don't
  want to thread the gates yaml path through `opts.gatesYamlPath`.
  The call signature is slightly awkward — 3 params, one of which
  is a module-shaped object, and a separate path in opts. Consider
  accepting a single config object: `resolveReviewerProvider({
  gateName, gatesRegistry, gatesYamlPath, yamlPath, configPath })`,
  OR document the recommended call shape in the JSDoc. Low priority;
  only one caller in Phase 14 (the 14-04 harness, not yet written).
