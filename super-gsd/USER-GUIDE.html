Section 01

What Is Super GSD?

Imagine you could tell your computer "build me a web app" and then walk away. When you come back, it's done — code written, tests passing, git commits clean, quality checked.

That's what Super GSD does. It's a framework that sits on top of Claude Code (Anthropic's AI coding tool). It turns Claude from a "helpful assistant that waits for your next instruction" into a fully autonomous software engineer.

🧠
Plans Its Own Work
Breaks big goals into phases, phases into tasks — without you having to spell it out.
⚙️
Executes Tasks
Writes actual code, runs tests, fixes bugs. Not just suggestions — real output.
💾
Manages Memory
Remembers what worked, what didn't, and what patterns to follow across sessions.
🛡️
Self-Quality-Checks
Reviews code before committing, catches problems early, enforces standards.
🔄
Survives Crashes
If it runs out of memory it saves its place and picks up exactly where it left off.
🎯
Right Brain, Right Job
Opus 4.7 xhigh for orchestration. Codex for research, planning, coding, verification, ATC, and gate checks.

How is this different from regular Claude Code?

Regular Claude CodeSuper GSD
You tell it what to do, one thing at a timeYou say "go" and it does everything
Forgets everything when you start a new chatRemembers decisions, patterns, and scripts across sessions
Uses one model for everythingKeeps Opus on orchestration and Codex on delivery work
No quality checksAutomatic quality gates before every commit
If it crashes, you start overCheckpoint system — picks up exactly where it stopped
Loads entire files into memory (wasteful)Queries only the relevant bits (80% less token usage)

How is this different from GSD 1.0?

Super GSD is built on top of GSD 1.0. Think of GSD 1.0 as the foundation (68 skills, 24 agents) and Super GSD as the upgrade that adds:

  • Autonomous orchestrator loop
  • Locked Opus/Codex routing
  • .planning/memory with local recall
  • CEO/Board deliberation for big decisions
  • ATC quality gates
  • Overwatcher signal map visualization
  • Token tracking and cost optimization
  • Checkpoint crash recovery

You keep everything GSD 1.0 has. Super GSD just adds more.

Section 04

Install — Step by Step

The One-Command Way

Open your terminal. Navigate to your project directory. Then run:

bash super-gsd/install.sh --init-project

That's it. The safe local installer will:

  1. Check that Node.js, Git, Claude Code, and Codex are visible
  2. Create the local .planning/ skeleton
  3. Create .planning/config.json if it is missing
  4. Create .planning/memory/ and MEMORY.md
  5. Create append-only metrics logs
  6. Create CLAUDE.md if it is missing
  7. Sync local registry files used by SGSD
  8. Leave ~/.claude and Claude autoApprove untouched

What If Something Goes Wrong?

"GSD 1.0 not found"
The installer will try to install it for you. If that fails, run this first:
npx get-shit-done-cc@latest
Then run the installer again.
"Node.js not found"
Install Node.js v22+ from nodejs.org (pick the LTS version).
"Permission denied"
Make the installer executable first:
chmod +x super-gsd/install.sh

The Explicit Way

Use the split modes when you want to see exactly what changes are local and what changes are global:

# Read-only checks
bash super-gsd/install.sh --doctor

# Project-local setup only
bash super-gsd/install.sh --init-project

# Optional global Claude agents, commands, hooks, templates
bash super-gsd/install.sh --install-global

# Optional and global: allow Claude Code to run without permission prompts
bash super-gsd/install.sh --enable-autoapprove

After Global Install — Merge Hook Registrations

If you run --install-global, SGSD merges hook registrations into ~/.claude/settings.json. The local --init-project path does not touch global Claude config.

Tell Claude
If you want global SGSD commands and hooks, run bash super-gsd/install.sh --install-global. Use --dry-run first if you want to preview the writes.

Then restart Claude Code (close and reopen). New global skills and hooks only load on startup.

Verify Everything Works

After restarting, run these checks:

# Check project state
/gsd-orchestrate status

# Check token tracking (empty is fine for new projects)
/gsd-token-audit --quick

# Test the memory system
sgsd-recall "orchestrator dispatch loop"

If all three work, you're good to go!

Permissions

Auto Mode & Permissions

Auto Mode Is Explicit

By default, Claude Code asks for your approval before running tools. SGSD's safe installer leaves global permissions alone. Auto mode is a deliberate separate command because it affects every Claude Code session on the machine.

What This Means
When autoApprove is set, Claude Code will read files, write files, run Bash commands, and spawn sub-agents without asking you first. Only enable this in project directories you own and trust.
Enable Auto Mode (global)
bash super-gsd/install.sh --enable-autoapprove
Disable Auto Mode (back to prompts)
claude config set --global autoApprove ""

The install script does not set autoApprove as part of --init-project or --install-global.

Sub-Agents and Auto Mode

All worker agents spawned by the orchestrator run with mode: "auto" in their agent definitions. This means they inherit the same no-prompts behavior. You don't configure this separately — it's baked into the agent files copied during install.

SettingEffectWhen to Use
bash super-gsd/install.sh --enable-autoapproveAll listed tools approved silentlyOnly on trusted machines/projects
autoApprove: ""Every tool use asks for permissionInteractive sessions, unfamiliar codebases
Sub-agent mode: "auto"Agent runs without user confirmationSet in agent definition files — don't change
Section 05

Your First Project

Starting From Scratch

Open Claude Code in your project directory and type:

/gsd-new-project

Claude will ask you questions about what you're building. Answer them. It will create:

  • PROJECT.md — What you're building and why
  • REQUIREMENTS.md — What the software needs to do
  • ROADMAP.md — The phases (steps) to build it
  • STATE.md — Where you are right now

Starting From an Existing GSD 1.0 Project

If you already have a .planning/ directory from GSD 1.0, Super GSD works with it automatically. Just install Super GSD and it layers on top.

The Magic Command

Once your project is set up (PROJECT.md, REQUIREMENTS.md, ROADMAP.md exist), type:

go

Or:

/gsd-orchestrate go
That's It
Claude enters the autonomous loop and starts building your software. You can walk away. Come back later. Check progress with /gsd-orchestrate status.

What happens when you say "go":

  1. Reads where it is in the project
  2. Figures out what to do next
  3. Does it (research, plan, code, test, verify)
  4. Commits the work
  5. Moves to the next thing
  6. Repeats until everything is done

Section 07

How The Autonomous Loop Works

This is the heart of Super GSD. Understanding it helps you trust it — and debug it when things go weird.

The Pipeline

01
READ
Where am I? (reads STATE.md header only)
02
CLASSIFY
What kind of work? (routing and gate policy)
03
QUERY
What do I already know? (searches memory)
04
COMPOSE
Build specific instruction prompt for worker
05
DISPATCH
Hand delivery work to Codex with evidence requirements
06
PROCESS
Read structured report from worker
07
CURATE
Save new patterns to memory
08
COMMIT
git commit — one per task, always
09
LOOP
Read STATE.md again → continue

Why Does It Keep Going?

Claude Code gives you another turn as long as every response includes a tool call (reading a file, running a command, etc.). The moment Claude sends only text with no tool call, the loop stops.

So the orchestrator makes sure every response includes at least one tool call. "Phase done!" is always paired with [Read STATE.md] — the read is the tool call that keeps the loop alive.

When Does It Stop?

Only 4 Exit Conditions
  1. All phases are done — Mission accomplished!
  2. Memory is 70% full — Saves checkpoint, stops. Say "go" to resume.
  3. It's stuck — Needs a human decision. Claude explains and waits.
  4. You say "stop" — Saves progress and stops.

Nothing else stops it. Not phase or milestone boundaries. Not time. Only these 4.

The Current Provider Split

Opus
Orchestrator
Makes decisions about what to do. Strategy, synthesis, judgment. Reads state, dispatches workers, synthesizes results.
$$$$ per token
Codex
Delivery Worker
Researches, plans, writes code, verifies work, and runs gate evidence. This is the default execution route.
$$ per token
Legacy Claude Workers
Disabled By Default
Sonnet and Haiku routes are legacy only in fresh-clone SGSD and are not fallbacks for Codex.
n/a
Section 08

The Memory System (.planning/memory)

The Problem It Solves

Regular Claude Code loads ALL memory files into every conversation. If you have 30 knowledge files, that's ~30,000 tokens eaten before Claude even reads your question.

Super GSD is smarter. It queries for relevant knowledge — like Google search instead of reading every book in the library.

The Memory Tree

.planning/memory/ ├── patterns/ ← "How to do X correctly" ├── anti-patterns/ ← "What NOT to do" ├── decisions/ ← "Why we chose X over Y" ├── error-rules/ ← "Always check for this mistake" ├── scripts/ ← "We already built a utility for this" ├── expertise/ ← "Domain knowledge for board members" └── domain/ ← "Business-specific knowledge"

File Frontmatter

Each knowledge file has a metadata header that controls how it gets matched:

---
title: Git Commit Discipline
tags: [git, commit, atomic]
keywords: [commit, git, atomic, never batch]
importance: 90        # 0-100, higher = more relevant
maturity: core        # draft → validated → core
---

Querying (Finding Knowledge)

Before dispatching a worker agent, the orchestrator searches memory:

sgsd-recall "auth middleware JWT patterns"

Returns the top matches with relevance scores. Only relevant results (~200–600 tokens) get injected into the worker's prompt — not all 30 files.

Curating (Adding Knowledge)

When a worker discovers something useful (a new pattern, a script it created, a bug it found), the orchestrator saves it to the memory system. Next time a similar task comes up, that knowledge is available.

You can also add knowledge manually — write a .md file with frontmatter and drop it in the right folder.

No API Key Required
Fresh SGSD projects use local markdown memory, not ByteRover. The recall path works offline and can be backed by optional private MCP knowledge sources when present.
Section 09

Strategic Decisions (CEO/Board)

When To Use This

You're building something and hit a fork in the road. "Should we use SQL or NoSQL?" "Should we build auth ourselves or use a third-party?" These decisions affect multiple phases and deserve real deliberation.

How It Works

/gsd-deliberate new

Claude asks what decision you need to make. It creates a structured brief, then spawns 4 board members with different perspectives:

Board Member 1
Architect
Technical, methodical
"Can we actually build this? What breaks at scale?"
Board Member 2
Pragmatist
Skeptical of ambition
"What's the simplest version that ships? What's the 80% solution?"
Board Member 3
Contrarian
Professionally paranoid
"What assumption hasn't been tested? What if this fails?"
Board Member 4
Moonshot
Thinks big
"Are we thinking too small? What's the 10x version?"

Each member gives their position (SUPPORT / OPPOSE / MODIFY). If they disagree, they debate (Round 2). The CEO synthesizes everything into a Decision Memo with:

  • Final recommendation
  • Who agreed and who didn't
  • Unresolved tensions
  • Trade-offs accepted
  • Next actions
The Gate — Don't Waste Tokens
Not every decision needs a 4-person board meeting. The system checks: "Does this affect 3 or more phases?" If not, it tells you to just decide and move on. This saves ~10,000 tokens per skipped deliberation.
Section 10

Quality Gates (ATC)

What's ATC?

ATC stands for "Air Traffic Control" — like at an airport. Before every commit gets "cleared for landing," it goes through a quality check. The depth of the check depends on how big the change is.

The 4 Tiers

SKIP
Tiny change (<10 lines, 1 file)
0 tokens
LITE
Small change (10–50 lines, 1–3 files)
~200 tokens
FULL
Medium change (50+ lines, 4+ files)
~500 tokens
GATE
Big change (new system, API, architecture)
~500+ tokens

The gate classifier assigns every change to a tier. Small = light checks. Big = full review. This saves time on trivial changes while catching problems on important ones.

The Safety Floor

Even if a change initially looks small, if it touches more than 3 files OR more than 100 lines, it gets bumped up to FULL automatically. This prevents a broad change from slipping through without review.

The Stuck Detector

If Claude makes the same tool call 3+ times in a row (writing the same file, running the same failing command), a hook fires and says: "You're stuck. Stop, re-read the error, try a different approach." This prevents infinite loops.

Section 12

Token Tracking — Watching Your Spend

Why Track Tokens?

Even on the Max plan (unlimited), tokens = time. More tokens = slower responses. Super GSD is designed to be efficient, but you should know where your tokens go.

The Token Log

Every agent dispatch gets logged to .planning/metrics/token-log.jsonl. Each entry records: when it happened, which phase and plan, which provider/model handled the work, what role, and estimated input/output tokens.

Checking Usage

# Quick summary
/gsd-token-audit --quick

# Deep analysis: trends, model distribution, optimization recs
/gsd-token-audit --full

# Which files cost the most tokens?
/gsd-token-audit --context-map

Where Do Tokens Go?

Section 13

Pausing and Resuming

Pausing

Say "stop" or "pause" or type /gsd-pause. Claude will:

  1. Write a checkpoint file (.planning/ORCHESTRATOR-CHECKPOINT.md) with exactly where it is
  2. Commit the checkpoint
  3. Stop

Resuming

Next time you open Claude Code, say "go" or "continue" or type /gsd-resume. Claude will:

  1. Find the checkpoint
  2. Read where it left off
  3. Delete the checkpoint (it's been consumed)
  4. Jump right back into the loop at the exact point it stopped
Zero Re-Explanation Needed
You don't need to re-explain anything. The checkpoint IS the context.

Automatic Pausing (Context Full)

If Claude's memory fills up (>70% context window), it automatically writes a checkpoint and stops. This is not a crash — it's a graceful exit. Just start a new conversation and say "continue."

What If Claude Crashes Without a Checkpoint?

The hooks write a lightweight checkpoint (.planning/ORCHESTRATOR-CHECKPOINT.json) after every git commit. So even if Claude crashes mid-session, there's usually enough breadcrumbs to resume from the last commit.

Section 14

Migrating From GSD 2.0 (Pi)

If you were using GSD 2.0 with the Pi harness (before Anthropic disabled OAuth), you have a .gsd/ directory with decisions, knowledge, requirements, and milestone data. Super GSD can import all of that:

/gsd-transition .gsd/

This will:

  1. Read your .gsd/DECISIONS.md — import decisions into .planning/memory
  2. Read your .gsd/KNOWLEDGE.md — import patterns and anti-patterns
  3. Read your .gsd/REQUIREMENTS.md — merge into .planning/REQUIREMENTS.md
  4. Map your milestones — completed work gets marked done, pending work becomes phases
  5. Write a migration report
Read-Only Import
Your .gsd/ directory is NOT modified or deleted. The migration is a read-only import.
Section 15

Troubleshooting

"The loop stops after one step"

The loop stays alive because every response includes a tool call. If Claude sends text-only, the loop dies. Usually means:

  • Claude thinks it hit an exit condition (check STATE.md)
  • A hook is crashing and breaking the chain (check ~/.claude/hooks/ for errors)
  • The CLAUDE.md file is missing or incomplete (re-copy from super-gsd/CLAUDE-OVERLAY.md)

"Permission denied" errors

Claude Code asks for permission before running tools. SGSD leaves global permissions alone unless you explicitly enable auto-approval:

bash super-gsd/install.sh --enable-autoapprove

"sgsd-recall returns no results"

Check that the memory tree has files:

find .planning/memory/ -name "*.md" | wc -l
# Should include MEMORY.md. If empty, re-seed:
bash super-gsd/install.sh --init-project

"Node.js version too old"

node --version  # Needs to be v22+

Update from nodejs.org.

"gsd-tools errors"

GSD 1.0's gsd-tools.cjs might warn about "unknown config keys." This is normal — Super GSD adds config keys that GSD 1.0 doesn't know about. The warnings are harmless.

"Checkpoint won't resume"

# Check the checkpoint file exists
cat .planning/ORCHESTRATOR-CHECKPOINT.md

# Check the JSON backup
cat .planning/ORCHESTRATOR-CHECKPOINT.json

# If both are missing, resume manually
/gsd-orchestrate go

"Signal map won't generate"

node ~/.claude/get-shit-done/templates/super-gsd/overwatcher/overwatcher-launcher.js

If it errors, the most common issue is that .planning/ is empty (no phases, no plans). Create at least one phase first.

"Token log is empty"

The token logger hook fires on Agent tool calls. If you haven't dispatched any agents yet, the log will be empty. Run /gsd-orchestrate next to dispatch one agent and check the log after.
