Owns the assignment

Reads the plan, dispatches work, answers from approved context, and checks the final evidence. Decisions needing your authority come back to you.

SGSD worker bridge

Delivers the message

Connects the exact project, worker, Codex thread and question. It is ordinary host code—not an extra model making decisions.

Codex worker

Does the bounded work

Uses its configured model, asks for missing context, receives the answer in the active turn, then continues and returns the required report.

Two separate changes.

The bridge enables communication. danger-full-access removes Codex’s filesystem sandbox. Removing the sandbox alone does not create a conversation; the bridge does that.

The connection

Approved target architecture. One adapter and App Server connection per active worker; the existing Fable session stays in its terminal.

On a narrow screen, scroll the diagram sideways. The steps below give the same flow in text.

What actually carries the conversation?

The adapter starts codex app-server and keeps a local input/output connection open. Codex can call sgsd_ask_orchestrator. The adapter publishes that question in .planning/worker-sessions/<worker-id>/.

Fable reads it with control.cjs status and sends an exact-target reply. The adapter returns that answer to Codex’s pending tool call. No chat messages are scraped from terminal panes.

Why the background launch matters

If Fable blocks waiting for the worker’s final output, it cannot service the question the worker is waiting on. It must launch the wrapper in the background, check the inbox, answer, and keep watching for completion.

“Automatic” therefore means the orchestration workflow does this on every dispatch. It does not mean a second Fable process starts when the original session is absent.

What the host commands look like

Implemented adapter CLI, shown with placeholders—not a transcript. Run against the matching project root in the same OS/shell environment as the worker. Fable launches the existing wrapper in the background and keeps checking this inbox; the adapter does not start another Fable.

node super-gsd/tools/codex-worker/control.cjs status --project "<project-root>" --owner "<owning-unit>"

node super-gsd/tools/codex-worker/control.cjs reply --project "<project-root>" --owner "<owning-unit>" --worker "<worker-id>" --request "<request-id>" --text "Use one shared receiver with separate project and session registrations."

node super-gsd/tools/codex-worker/control.cjs receipt --project "<project-root>" --worker "<worker-id>" --command "<returned-command-id>"

The host checks the active worker and question. A queued reply is not yet forwarded; an applied receipt confirms forwarding, not task success. Fable still waits for the wrapper result and validates the final report.

More connected.
Still bounded by the task.

These are workflow controls. With the OS sandbox removed, they are not a substitute for operating-system access restrictions.

Full access is a real permission change

The local SGSD profiles now request danger-full-access and approval never. Workers can access what the launching OS account can access. An advisory “do not edit” instruction is no longer enforced by a read-only sandbox.

The change is scoped to SGSD-owned dispatch configuration—not deleting your Codex installation or rewriting global authentication settings. Communication itself does not require removing a sandbox.

Inbox separation is routing, not isolation

Each project has its own worker records. Exact IDs prevent accidental cross-task replies through the control interface. A full-access process under the same OS account is not securely isolated from other project files.

There is no remote listening port for this connection. Cross-machine orchestration is outside this design.

Atlas is not the message bus

Questions and answers are bounded operational data in the project mailbox. Atlas remains the separate, content-free telemetry path for supported native events and run attribution.

Do not copy raw prompts, reasoning, tool payloads or code into telemetry. This diagram does not claim every possible metric is already captured.

Failures must stay visible

Unsupported App Server features, unexpected permission requests, disconnected processes, non-completed turns and deadlines fail explicitly—not as successful-looking reports.

Dynamic tools are experimental. Local CLI 0.153.4 initializes successfully without a model turn. Bash wrappers require native POSIX/WSL Node and Codex; Windows interop shims are rejected. A hard-killed adapter can require manual recovery of its exact thread claim.

The VTP DDIA excerpt separates delivery from application success. Its implication here: verify exact identity, the wrapper receipt and the report. Recover the existing task before considering a new worker. See the book passages and design cross-check.
