  • moved P3 Mission Control to top-right.

  • added in P3: two big red counters for remaining work — 9 phases and 47 sub-waves. These are the "how much is left in this milestone" gut-check.
  • added in P3: session cost box with Opus / Sonnet / Haiku broken out, total in green, per-phase subtotal. Computed from token-log.jsonl at standard API rates even though Max plan = OAuth.

Matches the Ctrl+O visual you already know from the main session.
  • renamed P5 script: was sgsd4, is now sgsd3 (since sgsd3 liveness is gone, the slot is free).

P3 Mission Control — source of truth for each block

  • Last phase built (green) → grep ROADMAP.md for highest [x] phase, or look at last git commit matching feat({NN}-*) pattern.
  • Current phase (orange) → .planning/STATE.md frontmatter current_phase.
  • Next phase → ROADMAP.md phase after current.
  • Current wave / next wave → parse active PLAN.md for <name>Wave N · ...</name> blocks, cross-reference with latest TaskCreate target that contains W\d+ or Wave \d+.
  • Phases remaining (red counter) → count of - [ ] phase lines in ROADMAP after current milestone header.
  • Sub-waves remaining (red counter) → sum of <name>Wave N · ...</name> blocks across every pending phase's PLAN.md (fallback: if PLAN not written yet, assume the roadmap phase summary's wave count).
  • Cost box → sum of total field in .planning/metrics/token-log.jsonl, grouped by model, multiplied by standard API rates (Opus $45/M blended, Sonnet $9/M, Haiku $2.4/M).
  • Agent roster → .planning/ORCHESTRATOR-LIVE.jsonl (new file written by orchestrator per decision D2-C), replayed to find started-but-not-ended agents.

P4 Ctrl+O stream — the data source

Claude Code writes a session log at ~/.claude/projects/<encoded-path>/<session-uuid>.jsonl with one JSON line per event: messages, tool_use blocks, tool_result blocks, thinking blocks. sgsd2 tails the newest file in the active project's session dir, parses each line, and renders:

  • For tool_use entries: one collapsed row (timestamp + tool name + summary of input) with an expandable body showing the full input JSON.
  • For tool_result entries: merged into the preceding tool_use row as a → stdout / → exit footer.
  • For Agent spawns: highlighted in magenta — these are the orchestrator dispatching sub-agents, the thing Jack most wants to track.
  • For TaskCreate/TaskUpdate: the "what's active right now" signal, rendered at the top of the stream so it stays visible.

FileSystemWatcher on the session dir catches appends in <100ms. Redraw budget: 1 frame per append, collapsed to 10fps max. No Haiku calls. No inference.

Layout reality check

  • At 1920×1080: all three columns fit comfortably. P1 is ~700px wide — plenty for claude TUI. P4 ~430px (tight for Ctrl+O bodies but readable). P3/P5/P6 each ~430px.
  • At 1440×900: min viable. P4 Ctrl+O bodies wrap at 40ch. P5 deferral ledger shows only 2 entries. Everything else fits.
  • At 1280×720 (laptop): layout collapses — drop P6 or stack it under P4. P3 stays. Not recommended but survives.

Questions for v3 (before we build this)

  1. Is P6 Dev Server worth keeping as its own pane? You didn't kill it but didn't keep it either. It exists because the browser verify gate needs Vite up. If you'd rather run Vite in a separate Warp tab, I'll drop P6 and give the space to P4 or P5.
  2. The Ctrl+O tool stream — do you want every tool call, or only Agent/TaskCreate/Bash? "Every" is closer to the real Ctrl+O view; "filtered" is less noisy.
  3. The red counters — do you want them to click through to the actual ROADMAP section? (tmux/terminal can't do real clicks but a hotkey like Ctrl+B + R could jump the main pane's cwd to open ROADMAP.md in your editor.)
  4. The last phase built row — you said green text. Should it show the one-liner from its commit, or just the phase number + name? I went with phase number + commit title stub.
  5. The cost box — should it flash red if any single phase exceeds a budget (e.g. >$50)? Useful as a "this phase is expensive, investigate" signal.
