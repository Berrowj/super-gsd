Design notes · v1 · 2026-04-11

This mockup is the visual anchor for Session 2 of the SGSD Warp layout design series (spec: 2026-04-11-sgsd-warp-layout-design.md). Every pane, colour, and signal maps to a real data source. No element here is aspirational unless explicitly marked TBD.

Pane inventory (maps to decision D3)

  • P1 Main Orchestrator — the actual claude --dangerously-skip-permissions session. Biggest pane, spans both rows on the left. This is where Jack types and reads live tool output. Everything else observes it.
  • P2 Liveness Monitor (sgsd3, new) — one huge word: ALIVE / THINKING / STUCK / DEAD. 1-second refresh. Signal sources: claude.exe pid + CPU, .planning/metrics/activity-log.jsonl last line age, STATE.md mtime, git log. Rules are hardcoded and hard to misread.
  • P3 Mission Control (sgsd1, rewritten) — milestone progress, phase progress, full wave list with names, agent roster, pulse, tokens/cost. This is the "where are we in the plan" pane. 10-second refresh.
  • P4 Narrative Feed (sgsd2, rewritten) — task tree (TaskCreate/TaskUpdate replay), Haiku-generated narrative (5-min cadence, token budget), and a recent-activity tail. This is the "what just happened" pane.
  • P5 Gate Verdict Board (sgsd4, new) — Verifier + ATC + Browser Verify + Deferral Ledger. Each gate is a card, colour-coded by verdict. Ledger entries older than 3 phases flash red (AUTO-REOPEN). Uses FileSystemWatcher so it repaints the instant a gate completes — no polling lag.
  • P6 Dev Server — npm run dev for the active project. Present in the workspace because the browser verify gate needs it up to pass; seeing its log alongside the orchestrator catches "forgot to restart vite" issues instantly.

Not yet rendered but considered and rejected: dedicated log tail (folded into P6), dedicated test runner (the executor runs tests inline), ByteRover explorer (too niche for a persistent pane), ATC log (folded into P5).

Agent visibility (decision D2)

P3's "Agents" block and P4's "Task Tree" both read from a new file: .planning/ORCHESTRATOR-LIVE.jsonl — the orchestrator appends one line per TaskCreate (agent start), one line per TaskUpdate (agent end), one line per BLOCKER. No env-var guessing, no sub-agent hook tagging. Authoritative.

Colours

  • ■ ALIVE / OK / PROVEN / ≤30s
  • ■ THINKING / WARN / IN PROGRESS / ≤5m
  • ■ STUCK / FAIL / UNPROVEN / 5–15m
  • ■ DEAD / PENDING / >15m
  • ■ agent name (P1, P3, P4)
  • ■ tool call / info
  • ■ Haiku token flow (P3 token line)

Layout dimensions

  • Min viewport: 1440×900. At that size every pane shows its full content without truncation.
  • Column ratio: 1.6 : 1 : 1 — main orchestrator gets the most real estate because reading it is the primary activity.
  • Row ratio: 1 : 1 — top row is fast-refresh (liveness + verdicts), bottom row is slower (mission control + narrative + dev server).
  • Failure mode at 1280×720: P4 and P6 collapse their internal sub-sections to 3 lines each. P3 hides waves 6–8 (still shows count). Never wraps.

Open questions the mockup does NOT answer

  • Does the liveness pane really need to be that big? Could it collapse into a status-bar ribbon across the top of Mission Control instead?
  • Is the gate verdict board better as a persistent pane or a toast-style overlay that only appears when a gate fails?
  • Should P6 (dev server) be conditional — i.e. hidden when the current project has no dev server?
  • Is the Haiku narrative worth the tokens now that the task tree is authoritative?
