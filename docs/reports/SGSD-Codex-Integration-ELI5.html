SGSD × Codex · ELI5

Where Codex fits in the full SGSD machine

Think of SGSD like a serious factory. Claude is still the foreman, the planner, the classifier, and the main mechanic. Codex does not become “another random worker”. Codex gets one narrow, useful job: independent reviewer.

The Big Idea
Claude builds.
Codex checks.

Not everywhere. Only where a second opinion is valuable: code review, adversarial challenge, and qualitative overproduction checks. That keeps SGSD sharper without turning it into a bloated circus.

What stays the same
Claude still classifies Claude still plans Claude still executes SGSD gates still rule Kill conditions still apply

Step 1 · What SGSD already is

Before Codex enters the picture, SGSD already has a strict job system. That matters because Codex only works if it slots into a real role.

1. Claude Opus = the conductor

Opus handles orchestration and synthesis. It decides what phase comes next and which engine should run.

orchestration milestone logic

2. Claude Sonnet = the builder

Sonnet does most of the actual implementation, verification, and current board work.

execution planning

3. Claude Haiku = the sorter

Haiku handles the cheap, frequent routing work: classify the task, pick context, keep the loop efficient.

classifier context picker
So the current story is: SGSD decides → Claude works → SGSD checks Codex only gets added where that loop is too one-vendor.

Step 2 · Why Codex is being added at all

Two reasons only: save Claude quota, and get a real second opinion where disagreement is valuable.

A

Claude quota is a real bottleneck

When SGSD runs long, Claude review tokens are expensive. Codex gives SGSD another review budget lane.

B

Same-vendor challengers share blind spots

If Claude checks Claude, the challenge is useful but limited. If Codex checks Claude, disagreement becomes stronger signal.

C

SGSD still hates bloat

Codex is not being added to “do more stuff”. It is only added to do a very specific job better.

Step 3 · The exact places Codex enters

This is the narrow lane. Codex touches review-shaped gates, not the whole orchestrator.

What Codex will do

Narrow lane
  • Phase-level ATC: big end-of-phase review.
  • Per-dispatch ATC: review of one specific change batch.
  • Adversarial verifier challenge: “what did the main verifier miss?”
  • Qualitative MUDA overproduction probe: catch YAGNI, duplication, over-engineering.

What Codex will not do

Still Claude
  • Not the classifier.
  • Not the main planner.
  • Not the main executor.
  • Not the primary mechanical verifier.
  • Not the whole board by default.

Step 4 · The visual pipeline

Here is the ELI5 version: SGSD sends work down the normal Claude rail, then selectively sends review-shaped work down the Codex rail.

Normal SGSD rail

1. Orchestrator decides

SGSD reads state, roadmap, gates, registry, and intent.

2. Claude classifies and plans

Haiku routes, Sonnet plans or executes, Opus synthesizes.

3. Claude builds the thing

The actual repo changes still happen in the main SGSD execution path.

New Codex review rail

4. SGSD asks: “Is this review-shaped?”

If no, stay on Claude-only path. If yes, consult the provider registry.

5. Codex reviews through a provider wrapper

Codex is called through a controlled substrate so SGSD still owns the contract, logs, and evidence paths.

6. SGSD stores the result in the same places

Same review files. Same JSONL logs. Same gate system. Different reviewer.

Step 5 · The one rule that makes this safe

Codex is only allowed in because it does not get to invent new evidence shapes.

Same outputs

If Claude would write a review file or JSONL record, Codex must write the same kind of artifact.

Same gate ownership

SGSD still decides whether a gate fires. Codex does not bypass gates. It only fulfills a reviewer slot inside them.

Same kill discipline

If Codex does not improve quality or save enough quota, the lane gets disabled. It does not stay around as decorative infrastructure.

Step 6 · The rollout is intentionally boring

This is the SGSD part: don’t flip behaviour and substrate in one move.

Phase 14

  • Build the provider wrapper.
  • Add provider registry.
  • Add Codex reviewer stub.
  • Keep `codex_enabled: false`.
  • No live routing changes yet.

Phase 15

Live but narrow

  • Make adversarial verifier cross-vendor.

  • Measure quota saved and extra issues found.

Step 7 · The child-version summary

If you had to explain it to someone in one breath:

SGSD is still a Claude-run factory. Codex is the outside inspector who walks in only when SGSD says, “this part needs an independent review.”

Step 8 · Why this is actually smart

Because it follows the same three SGSD rules already used everywhere else.

1. Evidence before machinery

Codex only stays if the metrics say it earns its keep.

2. Structure over vibes

The provider registry, same evidence contracts, and gate ownership stop it from becoming messy “AI glue”.

3. Retain then escalate

SGSD keeps the smallest working setup first, then escalates only when a stronger signal is needed.

4. Kill dead substrate

If Codex does not improve review quality or quota offload, SGSD turns the lane off instead of pretending it was useful.

What changes for you?

You do not get a second full orchestrator. You get a better SGSD. The system gains one new specialist: a Codex reviewer lane with real contracts, real logs, and a real off switch.

Final mental model
  • Claude remains SGSD’s brain and hands.
  • Codex becomes SGSD’s second pair of eyes.
  • SGSD itself remains the boss of the whole loop.
