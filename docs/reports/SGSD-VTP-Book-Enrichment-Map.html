The Enrichment Spine

The books were not used as decorative citations. Each book was turned into a design rule, each design rule was tied to an SGSD problem, and each problem was routed into a milestone and phase where Claude can act on it later.

1. Book Extract a durable design rule.

Example: startup UX must match the user's mental model.

2. Problem Attach it to a real SGSD pain point.

Example: `sg` should not surprise the operator with a new Claude window.

3. Design move Make the idea operational.

Example: define a startup command matrix and verify it mechanically.

4. Roadmap slot Assign the right milestone and phase.

Example: v1.6, Phase 26, Startup UX Contract.

5. Claude slot Leave an enrichment prompt.

Claude replaces the placeholder with evidence, risks, and checks.

Books gave doctrine

The books supplied durable engineering principles: usability, coupling, architecture boundaries, fitness functions, reliability, memory governance, and documentation discipline.

Research gave agent guardrails

Research papers were used as support where the book principles touched agent behavior: provider scheduling, retrieval failure, memory poisoning, autonomous guardrails, and evaluation risk.

Roadmap got sharper

The result is not "add more AI." The roadmap now says when to simplify, when to gate, when to measure, and when to delete.

Book Cards

Each card explains why the book was selected, the SGSD problem it addresses, and where it was placed in the proposed roadmap.

01

The Design of Everyday Things

UX, affordances, conceptual models

Why it was used
SGSD startup had a conceptual-model problem: what the user expected from `sg` was not always what the system did.
Idea extracted
Visible behavior must teach the correct model. A failed cockpit pane should look failed, not like a normal prompt.
Problem solved
Surprise boot behavior, confusing terminal ownership, and dashboard crashes that looked like idle PowerShell.
v1.6 Phase 26 Phase 29 Phase 30 v2.1
02

Don't Make Me Think

Usability, first-run clarity, obvious paths

Why it was used
The boot and setup path needed one obvious daily command, with advanced flags kept out of the main flow.
Idea extracted
Remove mental chatter. The user should not need to ask whether Claude or SGSD should be booted first.
Problem solved
Alias confusion, VTP setup confusion, and README paths that assumed repo history.
v1.6 Phase 26 Phase 30 v2.1 Phase 54
03

Writing Effective Use Cases

Behavioral requirements, actors, triggers, outcomes

Why it was used
SGSD commands needed to be described as promises, not only command names.
Idea extracted
Each command should have an actor, trigger, normal outcome, alternate outcome, and repair instruction.
Problem solved
Ambiguous startup flags and future command contracts with unclear success or failure behavior.
v1.6 Phase 26 v1.7 Phase 31 v2.1
04

Software Architecture for Developers

Just enough architecture, diagrams, constraints

Why it was used
The docs needed visual architecture without turning into a ceremonial design tome.
Idea extracted
Use generated maps, diagrams, and constraints that stay close to working software.
Problem solved
Stale command catalogs, tribal knowledge, and onboarding docs that explain history instead of current operation.
v1.6 Phase 30 v1.7 Phase 35 v2.1
05

Software Architecture in Practice

Quality attributes, views, interface specification

Why it was used
SGSD needed architecture that can be evaluated, not architecture that merely sounds coherent.
Idea extracted
Tie command envelopes, route ledgers, and failure scenarios to quality attributes.
Problem solved
Unclear definitions of reliability, restart safety, and command contract quality.
v1.7 Phase 31 Phase 35 v2.0 Phase 49
06

Fundamentals of Software Architecture

Fitness functions, architecture characteristics, chaos examples

Why it was used
Gates needed to prove value rather than existing because the process had grown them.
Idea extracted
A gate is a fitness function only if it objectively checks a property SGSD cares about.
Problem solved
Gate bloat, weak pass/fail definitions, and dashboard checks that are visible but not valuable.

A Philosophy of Software Design

Complexity, deep modules, simple interfaces

Why it was used
Command envelopes and gates can easily become shallow, noisy abstractions.
Idea extracted
Make the command contract small and deep: hide implementation complexity behind a stable envelope.
Problem solved
Overlarge schemas, bespoke regex parsing, and future tool APIs that leak internal complexity.

Clean Architecture

Domain-Driven Design

Strategic Monoliths and Microservices

Distribution tradeoffs, autonomy, split cost

Why it was used
SGSD could become a pile of small gates, tools, and dashboards that are expensive to coordinate.
Idea extracted
Do not split or add process unless autonomy, volatility, or ownership justifies the cost.
Problem solved
Process sprawl, duplicated checks, and gates that exist because adding one felt easy.

Gate effort should be aimed at the boundaries where change cost is highest.
Idea extracted

How Claude Should Use This

When a future Claude session promotes a milestone, it should not just cite the books. It should convert the relevant book rules into acceptance criteria, verification commands, and kill/defer conditions.

Rule 1

Start with the books for the milestone, then use research papers only to sharpen agent-specific risks.

Rule 2

Every enrichment slot must produce a design consequence, not a generic literature summary.

Rule 3

If a book argues for simplicity, Claude should delete or narrow scope before adding a new gate.

Rule 4

If a book argues for reliability, Claude should produce a failure case and expected observable result.

Teacher note

The best use of the VTP book corpus is not "more references." It is stricter planning. The book rule must change the work: a command contract, a test, a deleted gate, a provider boundary, a memory provenance field, or a restart scenario.
