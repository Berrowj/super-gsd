The Short Answer

The wrong move is to fork Warp and start building a native panel immediately. The right move is to make Warp the native operator layer around SGSD first.

Today

Use Warp's native surfaces

Workflows, project rules, skills, code review, launch configs, session sharing, and Warp Agent.

Next

Build read-only SGSD MCP

Give Warp Agent structured tools to ask SGSD what is running, blocked, reviewed, or spending tokens.

Later

ACP/native Warp work

Only after the bridge proves what SGSD needs from Warp as a generalizable platform feature.

ELI5

Think of Warp as the cockpit of a plane and SGSD as the autopilot plus engineering checklist. The cockpit gives the pilot buttons, screens, radio, maps, and warnings. The autopilot is what actually flies the route, checks rules, logs evidence, and knows whether it is safe to continue.

What makes Warp better than PowerShell?

Blocks, rich input, command search, native agent prompts, file/context attachment, code review, session sharing, and project-aware agent context. PowerShell runs commands. Warp wraps command work in an agent-friendly workspace.

What should stay SGSD-owned?

Phase truth, gates, verifier results, Codex review contracts, MUDA, token ledgers, release readiness, memory governance, and checkpoint recovery. Those are not UI features. They are delivery controls.

Can We Wrap Our Own Agents Like Warp Does?

Yes in several useful ways, but not all meanings of "wrap" are equal. The realistic path has five levels.

Level 1

Wrap Claude and Codex better

SGSD should launch supported CLIs so Warp still detects them and shows the utility bar.

Level 2

Wrap SGSD procedures as skills

Put SGSD operator skills under `.agents/skills/` so Warp Agent can discover and invoke them.

Level 3

Wrap SGSD state as MCP tools

This is the central bridge. Warp Agent asks tools like `sgsd_gate_status` and `sgsd_token_spend`.

Level 4

Wrap cloud-safe work as Oz agents

Good for scheduled docs audits or clean install checks. Not yet right for full local SGSD auto-mode.

Level 5

Native SGSD agent through ACP

Prepare for it, but do not depend on it until Warp's ACP support is stable enough to test.

Not today

First-party utility bar identity

Public docs do not show a stable API for registering arbitrary third-party local agents as first-class detected tools.

ELI5

MCP is like giving Warp a proper dashboard cable into SGSD. Without it, Warp has to look through the windshield and guess what the engine is doing. With it, Warp can read the actual gauges.

Where To Use Warp, Where To Use SGSD

This is the division that keeps the system powerful without becoming duplicated or confused.

Warp should own

  • Launching common commands through Workflow Search.
  • Operator prompts, voice, images, files, and block context.
  • Native code review and human comments.
  • Readable plans before SGSD turns them into phases.
  • Session sharing and phone monitoring.
  • Warp Agent as the supervisor/helper.
  • Notebooks, prompts, and reusable operator playbooks.

SGSD should own

  • Milestone and phase truth.
  • Autonomous loop and dispatch sequence.
  • ATC, verifier, MUDA, release readiness, and status consistency.
  • Token and context ledgers.
  • Codex/Claude review contracts.
  • Checkpoint and recovery behavior.
  • Memory governance and optional VTP integration.

Hard boundary: Warp Code Review can help the human inspect diffs. It does not replace SGSD ATC, verifier, release readiness, or MUDA gates.

Risks And Guardrails

Risk

Building against terminal scrollback

Terminal text is not a stable API. Use MCP and state adapters over `.planning` instead.

Risk

Making Warp mandatory

SGSD must remain usable in PowerShell, Windows Terminal, VS Code terminal, and CI.

Risk

Making VTP mandatory

VTP is a private knowledge base. The public/default path must degrade to SGSD docs and optional configured knowledge roots.

Risk

Cloud agents reading local-only files

Oz/cloud runs cannot see uncommitted local mission packets. Cloud-safe jobs need committed context and explicit environments.

Risk

Using Warp review as a gate

Warp Code Review helps humans inspect diffs. SGSD gates still decide whether work is accepted.

Risk

Forking Warp too early

Use workflows, rules, skills, MCP, and launch configs first. Upstream native changes after the need is proven.
