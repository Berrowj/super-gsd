What SGSD Is

SGSD means Super GSD: a structured, autonomous delivery layer around the normal GSD planning files. It turns a loose operator request into a phase, turns a phase into research and implementation steps, dispatches the right execution tools, checks the work through gates, records evidence, and advances the project state without needing the operator to babysit every transition.

In plain terms: SGSD is not just a prompt, a todo list, or a pile of scripts. It is an operating system for delivery. The important thing it adds is continuity. It keeps track of the current milestone, the current phase, the gate status, the handoff evidence, and the reasons decisions were made.

ELI5: imagine building a rocket with a checklist, a project manager, a test engineer, and a library of lessons learned. SGSD is the checklist plus the project manager plus the test engineer. VTP is the library. Gates are the “do not launch until this is true” checks.
Operator asksA human gives intent, constraints, priorities, or a milestone goal.

Research happensRepo, docs, MCP, VTP, and codebase context are gathered.

SGSD should always make the next action clearer than the previous action. Any SGSD artifact that does not help decide, verify, debug, or hand off should be treated as suspect until it proves its value.

How It Makes Life Better

SGSD improves delivery by reducing the amount of project state the operator has to keep in their head. The operator should be able to go to sleep, fly for three and a half hours, or come back after a forced restart and still know what happened, where the evidence is, what remains risky, and what the next phase should do.

Less Lost Context

Planning files, milestone summaries, phase folders, findings detail, and state files create a trail. The trail is what survives interruptions.

Less Blind Trust

Gates force the work to show evidence: tests, links, diffs, verification notes, screenshots, audits, or explicit known gaps.

Less Manual Glue

The orchestrator knows when to research, when to execute, when to call VTP, when to run ATC, and when to block instead of advancing.

Lifecycle From Idea To Done

The SGSD lifecycle is easiest to understand as a relay race. Each stage receives a baton, adds evidence, and passes a more structured baton to the next stage. The baton should never become less clear as it moves.

0. IntakeHuman request, active project state, constraints.
1. DiscussInteractive clarification when the phase itself needs shaping.
2. ResearchRepo scan, docs, VTP, risks, unknowns.
3. PlanDefine files, steps, gates, artifacts, expected outputs.
4. ExecuteMake changes or produce docs using controlled commands.
5. VerifyRun tests, ATC, browser checks, contracts, audits.
6. CloseSummaries, roadmap, state, next phase.

Phase 0: Intake

Intake turns a human instruction into a route. The orchestrator checks the active roadmap, requirements, and state. It decides whether the work is a discussion, research phase, implementation phase, verification phase, milestone close, or emergency recovery.

ELI5: before you start driving, you check where you are, where you are trying to go, how much fuel you have, and whether the road is closed.
Intake should emit a small route decision record every time. If something goes wrong later, you need to know whether the first wrong turn happened at classification.

Phase 1: Discuss

The recovered requirements state an invariant: /gsd-discuss-phase remains interactive while other stages can be autonomous. That is a good separation. Discussion is where human taste, priority, and strategic judgment belong. Execution should not repeatedly ask the same questions once the direction is set.

MUDA watch: do not turn every phase into a committee. Use interactive discussion only when the decision is genuinely strategic, ambiguous, or high-cost to reverse.

Phase 2: Research

Research gathers repo evidence, current docs, VTP signals, implementation constraints, and known failure modes. In SGSD v1.5, research-to-planning is one of the explicit VTP enrichment moments.

A good research artifact answers: what exists, what is missing, what is risky, what prior work matters, what VTP says, and what should be tested.

Phase 3: Plan

Planning converts research into a concrete execution shape. It should name files, commands, dependencies, acceptance criteria, gates, and fallback behavior. Plans are not valuable because they are long. They are valuable because they reduce wrong work.

A plan should include an “abort condition.” SpaceX-style hardening means you know what evidence would stop the launch, not only what evidence would make you feel good.

Phase 4: Execute

Execution should follow the plan but remain sensitive to code reality. This is where codex-exec.sh, local scripts, browser automation, dashboards, or targeted code edits happen. Execution outputs should be machine-readable where possible and human-readable where necessary.

Phase 5: Verify

Verification is the strongest trust layer. SGSD uses gates such as ATC, VTP enrichment checks, MUDA checks, provider contracts, edge guard, browser verification, and phase verifier behavior. The precise gate set depends on the route and artifact type.

Phase 6: Close

Closing a phase or milestone writes the durable memory: summaries, verification notes, roadmap changes, links to evidence, and next-step recommendations. The recovered transcript specifically mentioned milestone-close VTP cross-reference: summary generation gains a “Connections (library-backed)” section querying VTP for similar-milestone patterns and industry-standard gaps.

Relay Anatomy

Every SGSD command should relay information in the same shape: 

INPUT
  - operator intent
  - current state
  - target phase or milestone
  - constraints and acceptance criteria

PROCESS
  - classify
  - gather evidence
  - execute or enrich
  - verify

OUTPUT
  - status: pass | warn | block
  - artifacts written
  - evidence links
  - next action
  - reason codes
  - known residual risk
Standardize this relay contract everywhere. If every command returns a stable envelope, the cockpit, milestone close, and debug tooling can all consume the same shape instead of learning each script's private language.

Orchestrator Responsibilities

  1. Maintain situational awareness. Read roadmap, state, requirements, and relevant phase artifacts before acting.
  2. Select a route. Decide whether the work belongs in discussion, research, planning, execution, verification, audit, or milestone close.
  3. Constrain the work. Keep execution inside file scopes, acceptance criteria, and known user preferences.
  4. Call knowledge at the right time. Use VTP for enrichment where it can change the plan, not as filler.
  5. Run gates. Trigger ATC, VTP, MUDA, phase verification, provider contracts, edge guard, browser verification, or test gates as appropriate.
  6. Write durable memory. Update artifacts so the next agent or operator can resume.
  7. Surface risk. Tell the operator what remains uncertain, not just what passed.
ELI5: the orchestrator is like air traffic control for work. It does not fly every plane itself. It decides which runway, checks the weather, keeps aircraft separated, and refuses takeoff when a safety condition is missing.
The orchestrator should record route decisions as data, not prose only. Future automation can only improve routing if it can compare route choices against outcomes.

Gates And Information Relays

A gate is a decision point. It should say pass, warn, or block, and it should explain why. A gate is not a vibe check. It is a small court of evidence.

Artifact entersPlan, code diff, research, milestone summary, route event.
Gate reads contractExpected inputs, required evidence, known constraints.
Gate checksSchema, quality, risk, relevance, tests, waste, safety.
Gate emits verdictpass/warn/block plus reasons and artifact links.
Orchestrator routesAdvance, repair, escalate, or stop.

Gate Families

Gate Protects Against Evidence It Should Demand Red-Pen Check
ATC Uncontrolled execution, missing context, wrong route, incomplete handoff. Route decision, inputs, outputs, exit status, artifact list, next action. ATC should be a control tower, not a paperwork pile.
VTP Enrichment Gate Plans that ignore relevant library knowledge, research, meeting context, or known patterns. Query, hits, why each hit matters, decision changed or not changed. Reject “citation theater.” Every VTP hit should either affect the plan or be marked non-actionable.
MUDA Gate Process waste, redundant gates, bloated artifacts, slow handoffs, unnecessary work. Waste class, example, cost, recommendation, confidence. Run it where process cost is meaningful; sample small work.
Edge Guard Dangerous state transitions, boundary violations, telemetry drift, unexpected path behavior. Transition id, old state, new state, reason code, policy result. Best as a narrow boundary guard. Too broad and it becomes noise.
Phase Verifier Phase marked complete without required artifacts or checks. Phase directory, checklist, missing files, stale files, pass/fail details. Should fail loudly on missing required evidence.
Provider Contract Tool/provider output schema drift and silent integration breakage. Fixture, expected schema, actual output, diff, compatibility decision. Use fixtures for regression. Provider drift is sneaky.
Browser Verify Frontend claims that do not render, broken UI, visual regressions, interaction failures. URL, screenshot, console errors, tested viewport, interaction result. For visual work, screenshots are evidence. Text-only verification is weak.
Milestone Close Declaring victory without summary, learning, or next-state clarity. Completed requirements, failed/deferred items, VTP connections, next-phase candidates. Close must preserve learning, not only status.

Pass, Warn, Block

PASS

The artifact satisfies the contract and has enough evidence to advance.

WARN

The artifact can advance, but there is a known risk, missing nicety, or follow-up.

BLOCK

The artifact should not advance. The next action is repair, rerun, or human escalation.

Every block should include a repair command or repair instruction. A gate that says “no” without saying “what would make this yes” slows the whole system down.

MUDA Review

MUDA means waste. In lean thinking, waste is work that consumes time or attention without increasing value. SGSD needs MUDA checks because autonomous frameworks can become ceremony-heavy: more logs, more gates, more summaries, more dashboards, but not necessarily more shipped value.

Common MUDA Classes In SGSD

Waste Class How It Shows Up Fix
Over-processing Running heavyweight enrichment or verification for tiny, low-risk edits. Use risk-tiered gates. Sample low-risk work.
Waiting Long gates block autonomous progress while adding little evidence. Parallelize independent checks and timebox advisory gates.
Motion Artifacts scattered across folders with no links from cockpit or summaries. Every summary should link exact artifact paths.
Inventory Backlogs of generated plans, research, or findings that no one uses. Expire or archive stale artifacts. Connect active artifacts to decisions.
Defects Wrong route, stale state, broken provider contract, unverified UI. Put gates at the failure boundary, not after everything is already mixed together.
Overproduction Writing large reports when a small decision record would do. Match artifact size to risk and audience.
Unused talent VTP corpus exists but is not queried when strategy or risk decisions happen. Use bounded VTP calls at research-to-plan and milestone close.
ELI5: MUDA is when you spend an hour making a perfect label for a box that contains the wrong thing. The label is tidy. The work is still waste.
MUDA gates should produce deletion candidates, not only warnings. The highest-value waste audit says, “remove this step,” “merge these artifacts,” or “run this only on high-risk work.”

SpaceX-Style Hardening

“SpaceX gating” here means designing the system to survive real failure modes instead of only passing happy-path checks. The mindset is: make the system prove it catches the kind of mistake that would actually hurt you.

Hardening Principles

  1. Test the boundary that can fail. Do not test the dashboard if the dangerous part is the state transition.
  2. Use destructive imagination, not destructive commands. Simulate stale state, missing artifacts, wrong schema, irrelevant VTP hits, and broken test outputs.
  3. Make failure observable. A silent fallback is worse than a loud block.
  4. Prefer small blast-radius tests. Fixture-based provider contracts are better than live risky operations.
  5. Record the repair path. A failed gate should leave the operator knowing exactly what to do.

Recovered VTP Service-Enrichment Advice

The interrupted run successfully called VTP service enrichment for “Super GSD Orchestrator.” It returned eight recommendations with high confidence. The visible recommendations included:

  1. Add bounded evaluation loops where quality is hard to see directly. Apply only when the team cannot reliably tell whether changes improve accuracy, usefulness, or groundedness.
  2. Increase observability around the narrowest failure point. Log one decision boundary, one evidence bundle, or one failure class with stable IDs.
  3. Add guardrails at the boundary where the service can actually cause harm. Add one gate on one risky output path.
  4. Refine the workflow before increasing agent complexity. Insert or reorder one step before adding bigger automation.

The key pattern is conservative: improve the narrow failure point, avoid broad bloat, and add evaluation where quality is hard to see.

This is the most important VTP takeaway: do not add smarter agents until the workflow, evidence, and decision boundaries are visible. More agent power without clearer contracts creates faster confusion.
